Архітектурний опис системи: Система бронювання квитків
1. Загальний опис та Class Diagram
Опис предметної області
Система бронювання квитків призначена для автоматизації процесу пошуку рейсів, вибору вільних місць, створення замовлень та здійснення онлайн-оплати пасажирами. Вона забезпечує взаємодію між користувачами, розкладом рейсів, квитками та транзакціями замовлень. Адміністратори системи керують розкладом та переглядають аналітичні звіти.

UML Class Diagram (Діаграма класів)
Нижче наведено структуру основних класів, їх атрибутів, методів та зв'язків (асоціація, композиція):

Фрагмент коду
classDiagram
    class User {
        +int userId
        +string name
        +string email
        +login()
        +logout()
    }
    class Ticket {
        +int ticketId
        +float price
        +string seatNumber
        +string status
        +book()
        +cancel()
    }
    class Flight {
        +int flightId
        +string origin
        +string destination
        +DateTime departureTime
        +checkAvailability()
    }
    class Booking {
        +int bookingId
        +DateTime bookingDate
        +string paymentStatus
        +createBooking()
        +processPayment()
    }
    
    User "1" --> "*" Booking : makes
    Booking "1" *-- "*" Ticket : contains
    Flight "1" -- "*" Ticket : has
2. Шарова архітектура та Component Diagram
Архітектурний підхід
У проєкті використовується класична шарова архітектура (Layered Architecture), яка розділяє систему на логічні рівня для забезпечення модульності, зручності тестування та підтримки.

UML Component Diagram (Діаграма компонентів)
Фрагмент коду
graph TD
    Client[Presentation Layer: Клієнт / Веб-інтерфейс] -->|HTTP / REST API| Service[Business Logic Layer: Сервіс Бронювання]
    Service -->|SQL Queries| DataAccess[Data Access Layer: Репозиторій Бази Даних]
    DataAccess -->|Read / Write| DB[(База даних PostgreSQL)]
Пояснення ролі шарів:
Presentation (Клієнтський шар): Відповідає за інтерфейс користувача (UI) та взаємодію з ним (веб-сторінки, мобільний застосунок).

Business Logic (Бізнес-логіка): Містить правила обробки даних, бізнес-правила бронювання квитків та перевірку доступності місць.

Data Access (Шар доступу до даних): Відповідає за збереження даних, виконання SQL-запитів та взаємодію з базою даних.

3. Функціональні сценарії (Use Case та Sequence Diagrams)
Ключова функція: "Створити замовлення"
А. UML Use Case Diagram (Діаграма прецедентів)
Фрагмент коду
graph LR

    User --> UC2[Вибрати рейс]
    User --> UC3[Створити замовлення]

    Admin((Адміністратор)) --> UC5[Керування рейсами]

Б. UML Sequence Diagram (Діаграма послідовності)
Фрагмент коду
sequenceDiagram
    actor User as Користувач
    participant UI as Presentation (UI)
    participant BLL as Business Logic
    participant DAL as Data Access
    participant DB as База Даних

    User->>UI: Вибирає квиток і натискає "Бронювати"
    UI->>BLL: createBooking(flightId, userId)
    BLL->>DAL: checkSeatAvailability(flightId)
    DAL->>DB: SELECT * FROM tickets WHERE...
    DB-->>DAL: Дані про наявність
    DAL-->>BLL: Місце доступне
    BLL->>DB: INSERT INTO bookings ...
    DB-->>BLL: Замовлення створено
    BLL-->>UI: Підтвердження бронювання
    UI-->>User: Відобразити успішний статус
Текстове пояснення послідовності: Користувач ініціює процес бронювання через інтерфейс. Шар Presentation передає запит бізнес-логіці, яка перевіряє наявність вільних місць через шар доступу до даних. Після підтвердження наявності в базі даних формується запис про нове замовлення, і користувач отримує сповіщення про успіх.

4. Життєвий цикл об'єкта (State Machine Diagram)
Об'єкт: "Замовлення (Booking)"
Діаграма відображає стани, через які проходить замовлення квитка з моменту створення до завершення або скасування.

Фрагмент коду
stateDiagram-v2
    [*] --> New : Створено замовлення
    New --> PendingPayment : Перехід до оплати
    PendingPayment --> Paid : Успішна оплата
    PendingPayment --> Cancelled : Час вийшов / Скасовано
    Paid --> Completed : Квиток видано / Рейс завершено
    Cancelled --> [*]
    Completed --> [*]
Пояснення переходів:
New: Замовлення створене, але ще не оплачене.

PendingPayment: Користувач перейшов на етап оплати.

Paid: Оплата пройшла успішно, квиток зарезервовано.

Completed: Поїздка відбулася / квиток повністю використано.

Cancelled: Замовлення скасовано користувачем або через закінчення часу на оплату.

5. Загальний архітектурний опис проєкту
Мета проєкту: Створення надійного програмного забезпечення для швидкого та зручного бронювання квитків на рейси з використанням сучасної трирівневої архітектури.

Тип архітектури: Layered Architecture (Шарова архітектура) з клієнт-серверною взаємодією.

Основні компоненти: Клієнтський веб-інтерфейс, сервіс бізнес-логіки, репозиторій даних та реляційна база даних.

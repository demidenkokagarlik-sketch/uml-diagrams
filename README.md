1. Опис предметної області
Система бронювання квитків призначена для автоматизації процесу пошуку, резервування та оплати авіарейсів. Користувачі мають змогу переглядати доступні рейси, обирати місця та створювати замовлення. Адміністратори системи відповідають за керування розкладом рейсів та перегляд аналітичних звітів. Система забезпечує надійний зв'язок між клієнтом та базою даних за допомогою розділення на логічні шари. Кожне бронювання має свій життєвий цикл, що супроводжується перевіркою наявності місць та обробкою платежів.

2. UML Class Diagram (Діаграма класів)


Основні класи та їх зв'язки:

User (Користувач): Атрибути: userId, name, email. Методи: login(), logout().

Flight (Рейс): Атрибути: flightId, origin, destination, departureTime. Методи: checkAvailability().

Booking (Замовлення): Атрибути: bookingId, bookingDate, paymentStatus. Методи: createBooking(), processPayment().

Ticket (Квиток): Атрибути: ticketId, price, seatNumber, status. Методи: book(), cancel().

Зв’язки:

Асоціація: User (1) — (*) Booking. Один користувач може зробити багато замовлень (makes).

Асоціація: Flight (1) — (*) Ticket. Один рейс може мати багато квитків (has).

Композиція (ромб): Booking (1) ♦— (*) Ticket. Замовлення складається з квитків (contains). Якщо замовлення скасовується, квитки в ньому також анулюються (життєвий цикл квитка залежить від замовлення).

Наслідування (успадкування) не використовується, оскільки класи представляють різні сутності.

3. Архітектурний підхід (Шарова архітектура)


Система побудована за принципом багатошарової архітектури (Layered Architecture), що дозволяє розділити відповідальність між компонентами та полегшити масштабування і тестування.

Основні шари (Component Diagram):

Presentation Layer (Шар представлення): Клієнтський інтерфейс або веб-інтерфейс. Відповідає за візуалізацію даних та взаємодію з користувачем. Залежність: звертається до бізнес-логіки через HTTP / REST API.

Business Logic Layer (Шар бізнес-логіки): Сервіс бронювання. Містить правила обробки замовлень, перевірку доступності місць тощо. Залежність: звертається до шару даних через SQL Queries.

Data Access Layer (Шар доступу до даних): Репозиторій бази даних. Абстрагує роботу з базою даних. Залежність: виконує операції Read/Write (читання/запис) з базою даних.

База даних PostgreSQL: Фізичне зберігання даних.

Взаємодія: Кожен верхній шар залежить від нижнього, але не навпаки.

4. Use Case та Sequence Diagrams (Функціональність)


Ключова функція: Створення та оплата замовлення квитка.

Use Case Diagram (Діаграма варіантів використання):

Актор "Користувач" має сценарії: Увійти в систему, Вибрати рейс, Створити замовлення, Оплатити квиток.

Актор "Адміністратор" має сценарії: Керування рейсами, Перегляд звітів.

Sequence Diagram (Діаграма послідовності):
Сценарій: "Створення замовлення".

Користувач натискає "Бронювати" в UI.

Presentation (UI) надсилає запит createBooking(flightId, userId) до Business Logic.

Business Logic надсилає запит checkSeatAvailability(flightId) до Data Access.

Data Access робить запит SELECT * FROM tickets WHERE... до Бази Даних.

База даних повертає дані про наявність. Якщо місце є, Data Access повертає "Місце доступне".

Business Logic надсилає команду INSERT INTO bookings... через Data Access до Бази Даних.

База даних підтверджує створення замовлення.

Business Logic повертає підтвердження до Presentation (UI).

UI відображає користувачу успішний статус.

5. State Machine Diagram (Діаграма станів)


Об'єкт: Замовлення (Booking).

Стани та переходи:

New (Нове): Початковий стан. Замовлення щойно створене.

Перехід: "Перехід до оплати" → PendingPayment.

PendingPayment (Очікування оплати): Система чекає на підтвердження платежу.

Перехід: "Успішна оплата" → Paid.

Перехід: "Час вийшов / Скасовано" → Cancelled.

Paid (Оплачено): Кошти отримано, квиток заброньовано.

Перехід: "Квиток видано / Рейс завершено" → Completed.

Cancelled (Скасовано): Замовлення скасовано (користувачем або системою). Кінцевий стан.

Completed (Завершено): Послуга надана, рейс виконано. Кінцевий стан.
